# CU05 — Publicar y administrar canciones (web ARTISTA)

Se implementaron tres pantallas independientes con datos de NestJS/PostgreSQL: dashboard, publicación/edición y Mis canciones. No se implementó catálogo móvil, CU06 ni reproducción musical.

## Rutas y acceso

- Dashboard: `http://localhost:5173/artista`.
- Publicar: `http://localhost:5173/artista/publicar`.
- Mis canciones: `http://localhost:5173/artista/canciones`.
- Editar una canción propia: `/artista/canciones/:id/editar`.

Iniciar sesión con una cuenta que tenga ARTISTA y un perfil artístico creado. La cuenta demo existente puede utilizarse con su contraseña ya configurada. Desde Inicio/Mi perfil, **Espacio del artista** abre el dashboard; desde CU04, **Mi música** abre ese mismo espacio. CLIENTE recibe una explicación de acceso restringido; una cuenta ARTISTA sin perfil recibe el enlace para completar CU04.

Para ejecutar: iniciar PostgreSQL, ejecutar `npm --prefix backend run migration:run`, `npm run dev:backend` y `npm run dev:frontend`. Nest debe iniciarse desde la carpeta backend mediante esos scripts para utilizar su directorio de cargas local.

## Endpoints

Prefijo común: `/api/auth/artist-songs`. Todos exigen autenticación existente por cookie/Bearer y rol ARTISTA.

| Método | Ruta relativa | Función |
|---|---|---|
| GET | `/dashboard` | Totales reales, publicaciones, borradores y actividad derivada de registros propios |
| GET | `/options` | Géneros activos y lanzamientos que pertenecen al artista |
| GET | `/` | Listado propio con estado, búsqueda, género, orden y paginación |
| POST | `/` | Crear borrador |
| GET | `/:id` | Consultar canción propia |
| PATCH | `/:id` | Guardar metadatos permitidos |
| PATCH | `/:id/state` | Publicar o retirar a borrador conservando el registro |
| POST | `/:id/audio` | Cargar/reemplazar audio autorizado, campo multipart `file` |
| POST | `/:id/cover` | Cargar/reemplazar portada autorizada, campo multipart `file` |
| GET | `/:id/media/:kind/:name` | Descargar audio o consultar portada con control de propiedad |

Metadatos: `titulo`, `descripcion`, `generoId` y `lanzamientoId`. El título es obligatorio (2–150 caracteres tras recortar espacios); descripción máximo 2000. Género y lanzamiento pueden ser null en borrador. El estado se cambia en su endpoint específico. No se aceptan `artistaId`, roles, rutas de archivos ni duración enviada por el cliente.

Filtros de listado: `estado=borrador|publicado`, `q`, `generoId`, `sort=newest|oldest|title`, `page`, `pageSize` (máximo 50). La interfaz solicita cuatro filas por página para mantener la composición de la referencia. Todos los filtros se aplican en PostgreSQL y siempre incluyen el artista autenticado.

## Persistencia, autorización y publicación

Se aplicó `PublicarCanciones1794486000000`: añade `descripcion`, permite `archivo_audio_url` null y crea índice por artista/actualización. No se eliminaron ni reescribieron registros. Se mantiene `synchronize: false`; la reversión automática destructiva queda deshabilitada.

El artista se obtiene por el usuario autenticado en cada operación. No se utiliza un id de artista del frontend como permiso. Los accesos a canciones de otro artista devuelven 404; CLIENTE devuelve 403. Las operaciones sobre archivos tienen los mismos controles.

Un borrador admite metadatos incompletos y ningún audio. Publicar exige título, género activo, duración calculada y referencia a un audio WAV que realmente existe en almacenamiento. También se comprueba la propiedad de un lanzamiento asociado. Los metadatos de una canción publicada no pueden romper esas condiciones. Retirar una publicación solo cambia su estado a borrador.

Los cambios que pueden competir sobre una canción usan transacciones y bloqueo de fila. Las cargas generan nombres UUID y escriben con exclusión (`wx`), sin sobrescribir archivos ni admitir rutas arbitrarias. Si falla la transacción que asocia un archivo nuevo, se elimina ese archivo recién creado. Los archivos sustituidos se conservan localmente; no se borran datos previos.

El formulario crea primero un borrador, almacena y valida archivos, y solicita publicación al final. Si una carga falla, no anuncia éxito. El borrador o los cambios ya guardados se conservan para poder corregir y reintentar; no se simula una transacción única entre varias peticiones HTTP.

## Audio y portada

**Audio habilitado:** WAV RIFF PCM entero, formato 1, sin compresión; 1–2 canales, 8–192 kHz, 8/16/24/32 bits, hasta 50 MiB. Se valida extensión, MIME, firmas RIFF/WAVE, tamaños de chunks, bloque, tasa de bytes, alineación de muestras y datos. La duración se calcula en el servidor a partir de datos/tasa y se guarda redondeada a segundos. No se acepta una duración manual.

**No habilitado:** MP3, FLAC, WAV flotante, WAV extensible y audio comprimido. La interfaz y la API lo indican expresamente. No se instaló un decodificador/transcodificador ni se simuló soporte.

**Portada:** PNG/JPG cuadrado, mínimo 1200 × 1200 px, máximo 2 MiB, 4096 px por lado y 8 megapíxeles. Se reutiliza la validación de CU04 y se añade comprobación de extensión y dimensiones de portada. PNG también comprueba estructura/CRC e información comprimida. La portada es opcional; si se proporciona debe cumplir esas reglas.

Los archivos se almacenan realmente en `backend/uploads/songs/`. El progreso mostrado corresponde al envío HTTP; al llegar a 100%, la interfaz distingue validación/almacenamiento de éxito definitivo.

La carga local solo está habilitada en desarrollo. Producción requiere almacenamiento persistente apropiado. Todos los archivos de CU05, incluso los de canciones publicadas, permanecen bajo acceso de propietario en este bloque; la lectura de catálogo se desarrollará en el punto siguiente. No existe una carpeta estática pública que exponga borradores. Audio se descarga como adjunto; no se añadió reproductor.

## Dashboard y diseño

Nombre artístico, canciones, borradores, lanzamientos y fechas proceden de PostgreSQL. Los contadores incluyen ceros reales cuando corresponda. Actividad reciente se deriva de la última actualización de canciones propias; no simula eventos de seguidores ni reproducciones.

Se mantuvieron header, sidebar, hero, tarjetas, zonas de carga, radios de estado, filas grandes y paginación de las referencias. Las ondas de las filas son decoración, no una forma de onda calculada del audio. Los módulos futuros informan que no están disponibles; no abren pantallas falsas.

## Diferencias y pendientes

- Se reutilizaron ilustraciones individuales existentes. El retrato y los audífonos son coherentes con Sonic Ledger, pero no son idénticos a los tres gráficos de referencia. Las portadas de ejemplo del prototipo no se incluyeron como contenido ficticio: cada canción muestra su portada real o un marcador musical.
- Los números, títulos, fechas y cantidad de filas dependen de los datos de la cuenta; no se copiaron cifras del prototipo.
- MP3/FLAC y almacenamiento de producción quedan pendientes de infraestructura/formato, explícitos en interfaz y API.
- No se implementaron estadísticas de audiencia, monetización, conciertos, historial, favoritos, playlists, reproducción completa ni catálogo móvil.
- No se avanzó al punto 7.
