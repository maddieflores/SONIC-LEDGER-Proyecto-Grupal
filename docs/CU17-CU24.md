# INFORME TÉCNICO DE IMPLEMENTACIÓN — CU17 + CU24
## SONIC LEDGER — SPRINT 3, BLOQUE 3: Cancelación de Conciertos y Estadísticas de Ventas/Asistencia

---

### 1. Resumen Ejecutivo

En este bloque se implementaron de forma integral y coordinada los casos de uso **CU17 (Cancelar Concierto)** y **CU24 (Consultar Ventas y Asistencia)** para la plataforma **Sonic Ledger**, garantizando la integridad transaccional de la base de datos PostgreSQL, la seguridad RBAC para organizadores y administradores, la coherencia del ciclo de vida de los eventos y tickets, y la visualización de analíticas reales en tiempo real sin simulación ficticia de reembolsos ejecutados.

- **CU17 — Cancelar Concierto**:
  - Restringido estrictamente al rol `ORGANIZADOR` propietario del concierto o a usuarios con rol `ADMIN`.
  - Aplicable exclusivamente a conciertos en estado `PUBLICADO` (los borradores mantienen su ciclo independiente de edición y descarte sin constituir una cancelación de evento público).
  - Exige de forma obligatoria un motivo de cancelación (`motivoCancelacion`), registrando además la fecha/hora exacta (`canceladoEn`) y el identificador del usuario responsable (`canceladoPorId`).
  - **Transaccionalidad con bloqueo pesimista (`pessimistic_write`)**: Dentro de una única transacción de TypeORM, se bloquea la fila del concierto y se ejecutan las siguientes acciones en cascada:
    1. Transición de estado a `CANCELADO`.
    2. Cierre definitivo de venta e invalidación inmediata de todos los tickets digitales emitidos (`estado = 'INVALIDADO'`, `motivoInvalidacion = 'CONCIERTO_CANCELADO'`).
    3. Anulación de órdenes pendientes de pago (`estado = 'CANCELADA'`).
    4. Registro de obligación de devolución en órdenes confirmadas (`reembolsoEstado = 'PENDIENTE_REEMBOLSO'`), sin fingir transferencias de dinero reales ni ejecutar llamadas falsas de WizPay.
    5. Liberación inmediata de todas las reservas de cupo temporales activas (`liberada = true`).
    6. Inhabilitación de tokens QR: cualquier escaneo en puerta por parte de un `VERIFICADOR` es rechazado de inmediato con `resultado = 'INVALIDADO'` y mensaje explícito de cancelación.
    7. Acceso público transparente: el concierto cancelado se oculta del catálogo principal, pero sigue siendo accesible mediante URL directa mostrando un banner de cancelación y deshabilitando la compra de entradas.

- **CU24 — Consultar Ventas y Asistencia**:
  - Servicio analítico dedicado (`EstadisticasService`) desacoplado de los flujos transaccionales de compra y validación.
  - Métricas agregadas reales calculadas directamente de PostgreSQL (sin consultas N+1 ni datos estáticos de relleno):
    - **Aforo y Ocupación**: `cupoTotal`, `entradasVendidas`, `reservasActivas`, `cuposDisponibles`, `porcentajeOcupacion` (%).
    - **Órdenes de Compra**: `totalOrdenes`, `ordenesConfirmadas`, `ordenesPendientes`, `ordenesFallidasOExpiradas`.
    - **Recaudación Bruta en BOB**: `ingresosConfirmadosBob` con indicación visual obligatoria de simulación (`PAGO DE PRUEBA — SIMULADO`).
    - **Control de Asistencia**: `ticketsEmitidos`, `ticketsUtilizados` (validados en puerta), `ticketsPendientesIngreso`, `ticketsInvalidados`, `tasaAsistenciaPorcentaje` (%).
    - **Desglose por Categoría**: Tabla analítica con precios unitarios congelados, cupos, ventas, reservas, recaudación y barras de progreso de ocupación.
    - **Métricas para Eventos Cancelados**: Preservación íntegra de estadísticas históricas junto al monto total pendiente de devolución (`montoPendienteReembolsoBob`) y cantidad de órdenes afectadas (`ordenesPendienteReembolso`).

### 3. Reglas de Negocio y Transaccionalidad (CU17)

#### Matriz de Autorización RBAC
| Operación | CLIENTE | ARTISTA | ORGANIZADOR Propietario | ORGANIZADOR Ajeno | VERIFICADOR | ADMIN |
|---|---|---|---|---|---|---|
| Cancelar Concierto | Denegado (403) | Denegado (403) | **Permitido (200)** | Denegado (403) | Denegado (403) | **Permitido (200)** |
| Ver Estadísticas de Ventas | Denegado (403) | Denegado (403) | **Permitido (200)** | Denegado (403) | Denegado (403) | **Permitido (200)** |
| Consultar Cancelación en Público | Permitido (200) | Permitido (200) | Permitido (200) | Permitido (200) | Permitido (200) | Permitido (200) |

#### Transacción Atómica de Cancelación
```
BEGIN TRANSACTION;
  -- 1. Bloqueo pesimista del concierto
  SELECT * FROM conciertos WHERE id = :id FOR UPDATE;

  -- 2. Validación: sólo si estado == 'PUBLICADO'
  UPDATE conciertos SET estado = 'CANCELADO', motivo_cancelacion = :motivo, cancelado_en = NOW(), cancelado_por_id = :userId;

  -- 3. Invalidar todos los tickets del concierto
  UPDATE tickets SET estado = 'INVALIDADO', motivo_invalidacion = 'CONCIERTO_CANCELADO' WHERE concierto_id = :id;

  -- 4. Anular órdenes de compra pendientes
  UPDATE ordenes_compra SET estado = 'CANCELADA' WHERE concierto_id = :id AND estado = 'PENDIENTE';

  -- 5. Registrar obligación de reembolso en órdenes confirmadas
  UPDATE ordenes_compra SET reembolso_estado = 'PENDIENTE_REEMBOLSO' WHERE concierto_id = :id AND estado = 'CONFIRMADA';

  -- 6. Liberar reservas de cupo activas
  UPDATE reservas_cupo SET liberada = true WHERE concierto_id = :id AND liberada = false;
COMMIT;
```

#### Tratamiento de Pagos y Reembolsos (Integridad de Cartera)
- Las órdenes confirmadas asociadas a conciertos cancelados pasan a `reembolsoEstado: PENDIENTE_REEMBOLSO`.
- **No se altera el saldo ficticiamente**: No se emiten reembolsos automáticos ni se invoca una pasarela inexistente. El sistema registra fielmente la obligación de devolución para su posterior liquidación manual o proceso administrativo por parte del organizador.
- Las órdenes pendientes de pago se anulan inmediatamente, liberando cualquier reserva.

### 4. Métricas e Indicadores de Analítica (CU24)

#### Fórmulas de Cálculo
1. **Porcentaje de Ocupación**:
   $$\text{porcentajeOcupacion} = \text{round}\left(\frac{\text{entradasVendidas}}{\text{cupoTotal}} \times 100\right)$$
   *(Si $\text{cupoTotal} = 0$, resulta 0%).*
2. **Cupos Disponibles**:
   $$\text{cuposDisponibles} = \max(0, \text{cupoTotal} - \text{entradasVendidas} - \text{reservasActivas})$$
3. **Ingresos Confirmados (BOB)**:
   $$\text{ingresosConfirmadosBob} = \sum (\text{item.precioUnitario} \times \text{item.cantidad}) \quad \forall \text{ órdenes confirmadas}$$
4. **Tasa de Asistencia en Puerta**:
   $$\text{tasaAsistenciaPorcentaje} = \text{round}\left(\frac{\text{ticketsUtilizados}}{\text{ticketsEmitidos}} \times 100\right)$$
   *(Si $\text{ticketsEmitidos} = 0$, resulta 0%).*
5. **Monto Pendiente de Reembolso**:
   $$\text{montoPendienteReembolsoBob} = \sum \text{orden.total} \quad \forall \text{ órdenes con } \text{reembolsoEstado} = \text{'PENDIENTE\_REEMBOLSO'}$$
